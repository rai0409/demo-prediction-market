# V2 Balance History Contract — Phase 3B-2 design

PRODUCTION_MIGRATION = NOT_AUTHORIZED
HISTORY_IMPLEMENTED = false
FEATURE_FLAGS_ENABLED = false

This is a normative extension of `v2-clob-execution-contract.md`. It specifies required future behavior; current code and the isolated model do not implement it. No existing endpoint, CLI, or response is enabled by this document.

## 1. Problem and scope

V1-derived allocations, reserve/split/merge events, order-collateral events and V2 trade rows use independent IDs and different timestamps. These do not establish a common bucket order; split/merge does not preserve position before/after snapshots. In the existing one-trade fixture, changing SELL_PROCEEDS before/after from 0/15000 to 1/15001 leaves delta correct and currently passes reconciliation although the final account has 15000. Comparing every historical after value with the current balance would reject legitimate later activity. A complete post-boundary mutation history is required; the V1 past cannot be reconstructed as an invented sequence.

## 2. Bucket identity and baseline

A bucket key is a typed tuple, never a concatenated string:

| `kind` | `account_id` | `market_id` | `outcome` | authoritative value |
|---|---|---|---|---|
| `POINT_AVAILABLE` | nonempty | NULL | NULL | `point_accounts.available_micro` |
| `POINT_LOCKED` | nonempty | NULL | NULL | `point_accounts.locked_micro` |
| `SHARE_AVAILABLE` | nonempty | nonempty | YES/NO | `outcome_positions.available_shares` |
| `SHARE_LOCKED` | nonempty | nonempty | YES/NO | `outcome_positions.locked_shares` |
| `MARKET_RESERVE` | NULL | nonempty | NULL | `market_reserves.reserve_micro` |

Point and share units never mix. Point buckets are per account across markets; share buckets are per account, market and outcome. Market reserves are per market. Engine is `collateralized_clob_v2`; source rows must belong to it. Existing row keys and foreign keys remain authoritative. `market_reserves.net_complete_sets`, supply state and audit are independent conservation inputs, not a sixth balance bucket. Every value and intermediate arithmetic is an integer in [0, 9223372036854775807]; negative delta is permitted only within checked before/after arithmetic. No SQLite REAL promotion is accepted.

## 3. Checkpoint and bucket lifetime

At V1→V2 migration, after preflight and schema rebuild but **before COMMIT**, under the same transaction and verified external writer exclusion, validate V1/V2 schema, foreign keys, integrity, audit chain, all existing accounting invariants, IDs, sequences and hashes. Create one complete generation, checkpoint and bucket record for both point buckets of every existing account, both share buckets of every existing position, and each existing market reserve, including zero values. The checkpoint value is the actual current value at the boundary; no invented events, old-row rewrites or audit hash modifications are allowed. Store format version, generation ID, boundary metadata, per-kind counts, canonical sorted key/value digest, and the existing audit-chain terminal hash. Compute digest from an explicitly specified canonical UTF-8 serialization: JSON array `["balance_checkpoint_v1",generation_id,[[kind,account_id,market_id,outcome,value],...]]`, sorted lexicographically by the UTF-8 bytes of a canonical JSON representation of the key tuple, compact separators, `ensure_ascii=false`, no NaN, SHA-256 lowercase hex. Identity fields are nonempty where applicable and must not be normalized. Record original V1 schema/row/audit verification evidence separately; missing or duplicate bucket, malformed metadata, digest/count mismatch or mismatched boundary state aborts migration.

A post-checkpoint account, position or reserve row starts at zero for each new bucket. Its creation, zero-valued bucket registration and any nonzero mutation are atomic with its operation; preexisting bucket keys cannot be reused after deletion. For this phase delete/rekey of account, position or reserve rows is forbidden, including zero rows. A newly created row with nonzero initial balance is rejected; writers must create zero then mutate through the guarded path. The registered bucket set and live rows must match exactly. Checkpoint and bucket records are immutable. A zero baseline requires no fabricated historical operation. Read-only verification never repairs data.

## 4. Proposed schema and integrity keys

Names below are implementation contract, not existing tables. All IDs and counters use checked SQLite INTEGER. Schema validator must verify exact tables, columns, relevant checks, unique keys, FKs, indexes and enforcement triggers. Every connection uses `foreign_keys=ON` outside the documented isolated rebuild window.

- `balance_history_generation`: exactly one committed generation, `generation_id` nonempty PK, `format_version=1`, `checkpoint_count` and `checkpoint_sha256`, `audit_boundary_hash`, boundary/schema metadata and a finalized flag constrained to 1 in any committed database. An incomplete or extra generation fails closed.
- `balance_history_bucket`: `bucket_id INTEGER PRIMARY KEY`, generation FK, typed identity fields as section 2 with CHECKs, `opening_value`, `origin` (`checkpoint` or `created`), and creation operation reference for `created`. Unique identity is enforced using separate partial UNIQUE indexes for point `(generation_id,kind,account_id)`, share `(generation_id,kind,account_id,market_id,outcome)` and reserve `(generation_id,kind,market_id)`; do not rely on nullable UNIQUE semantics. `origin=created` requires opening_value=0 and a finalized creation operation; checkpoint membership and digest are independently checked.
- `balance_history_operation`: unique `operation_id` generated before mutations, source type, source ID and idempotency identity, immutable finalized manifest. Sources are `point_supply_event`, `point_allocation_event`, `reserve_event`, `order_collateral_event`, `v2_trade`, and `bucket_create`; source IDs are typed by source type and must resolve to the actual row; creation identity is the full bucket owner key. Unique `(source_type,source_id)` is enforced with non-null source IDs at finalization. Distinguish operation identity from API idempotency keys; no user-controlled key may collide across scope.
- `balance_history_event`: `event_seq INTEGER PRIMARY KEY AUTOINCREMENT`, generation/bucket/operation references, nonempty `role`, before, signed delta and after. Enforce integer storage and checked `before + delta = after` without overflow; zero delta is allowed only for explicit `BUY_REFUND` or explicitly defined zero-bucket creation metadata, not ordinary movements. Unique `(operation_id,bucket_id,role)` and indexes `(generation_id,bucket_id,event_seq)` and `(operation_id,role)` are mandatory. FKs to generation, bucket and finalized operation are mandatory; polymorphic source references are verified by type-specific checks. `bucket_create` registers the opening zero and has no movement event. Source events, history and bucket mutations must have the same engine and exact account/market/outcome/asset/bucket linkage.

A checkpoint commits with generation finalization and no post-boundary events. For later writes, the operation manifest enumerates the exact expected bucket roles and source link. A transaction-scoped operation context lives in protected SQLite tables, keyed by a unique operation ID and used only while holding the write transaction; cleanup is part of that transaction. Triggers reject missing, duplicate, mismatched or ambiguous context. Because SQLite has no COMMIT trigger, history event references must use a `DEFERRABLE INITIALLY DEFERRED` FK to a finalization row that exists only after all source rows, roles and events have been validated; a deferred FK prevents committing unfinalized events. This mechanism must be proven with foreign keys on and transaction/restart tests; it is not acceptable to rely on a boolean supplied by a caller. The migration's temporary FK-off window must explicitly verify no dangling finalization references before COMMIT and restore/check FK outside the transaction. Context rows cannot survive a successful commit, including operations with no balance movements. Implement this with a NOT NULL constant guard key in every context row referencing a protected, permanently empty `balance_history_context_must_be_empty` table via a `DEFERRABLE INITIALLY DEFERRED` foreign key. Context insertion is allowed inside the transaction but COMMIT fails until the context row is deleted. Schema validation must require this FK and enforce that the sentinel remains empty via a validated trigger that aborts all INSERT, UPDATE and DELETE on the sentinel; tests must prove it on every supported SQLite configuration. Event rows separately reference finalized operation rows by a deferred FK. The writer finalizes the source/role manifest, inserts its finalization row, and deletes context before COMMIT. During the isolated FK-off migration window, explicitly assert both context and sentinel tables are empty before COMMIT. If this protocol cannot be enforced on a supported connection, fail closed.

## 5. Ordering, atomicity and capture choice

Choose **database triggers plus an operation context/finalization protocol**, rather than a helper-only ledger. A helper-only approach is simpler but can be bypassed by an unconverted SQL writer; guarded row triggers observe each actual INSERT/UPDATE and fail closed when context is absent. Each live balance change and its history event are recorded in the same SQLite write transaction. A row update changing two buckets creates one event per changed bucket in an explicitly fixed kind order: POINT_AVAILABLE then POINT_LOCKED; SHARE_AVAILABLE then SHARE_LOCKED. Multi-row SQL updates are prohibited on protected balance tables: writers must issue one row mutation at a time, with deterministic operation steps. Each context step authorizes exactly one typed row key and its expected bucket roles; the first trigger that sees any other key aborts the statement and transaction. The implementation must test that a multi-row statement cannot reuse one authorization. SQLite single-writer serialization plus event INSERT order determines the global order of **committed** events; it is not an operational exclusion gate for old writers.

`AUTOINCREMENT` prevents reuse of previously committed IDs, not reuse of IDs from rolled-back transactions. An aborted transaction rolls back its mutations, history and sequence effects together; gaps and rolled-back ID reuse are legal. Do not require contiguous IDs, use wall clocks as ordering proof, or infer missing events from numeric gaps. Every per-bucket chain starts at its registered opening value, orders by committed `event_seq`, requires event.before = previous after, checked before+delta=after, and requires the final after (or opening value if no events) to equal the live value. Check generation/bucket coverage, finalized operation manifests and source-to-role cardinality independently: a missing event cannot pass merely because net change is zero. Retry checks existing idempotency/source result before creating context or changing balances; replay returns the stored result with no new history, even for a zero refund.

All protected tables, triggers, metadata, context and finalization rules are part of versioned schema validation. Old binaries, foreign_keys=OFF, disabled/missing triggers, direct DDL, REPLACE/delete/rekey or absent context must fail closed before writers start. Ordinary `INSERT OR IGNORE` that inserts nothing creates no bucket/history; an actual new row does. In particular, SQL no-op updates must not produce ordinary movement events. For `BUY_REFUND=0`, finalization emits exactly one explicit zero event through the same protected operation context, even if no balance update occurred, and verifies its before=after at its ordered step. History events are evidence of mutations, not additional monetary mutations; do not sum them as extra value or apply them again. Source and history tables are append-only after finalization. DB-owner tampering that rewrites all histories, manifests, checkpoints and hashes cannot be proven absent solely by an unkeyed local digest; external independently protected checkpoint/audit anchors are required for that stronger threat model and remain an operational prerequisite.

## 6. Writer obligations and reconciliation

| Current source path / function | Actual changes | Required event/source obligations |
|---|---|---|
| `app/collateral_ledger.py:_ensure_treasury_account`, `allocate_v2_points_to_participant` | create account; source and destination available points | zero bucket registration; `point_allocation_event` debit/credit map exactly to `collateral_ledger_entries` and allocation before/after |
| `bootstrap_v2_point_supply` | create treasury; issue into available points; update supply | zero registration, `point_supply_event` bootstrap credit and existing collateral ledger/audit; burn is schema-enumerated but no current burn writer was found, so future burn is forbidden until mapped and tested |
| `create_collateral_market` | create market reserve at zero | `bucket_create` zero registration; market status changes alone are not balance events |
| `_complete_set_operation`, `split_complete_sets`, `merge_complete_sets` | available points, reserve points, YES/NO available shares; create position | `reserve_event` with four independently captured bucket changes and zero registrations as needed; match existing point/reserve ledger and quantity, capture shares previously missing |
| `reserve_v2_order_collateral` | BUY point or SELL share available→locked | `order_collateral_event` exactly two history events matching existing `order_collateral_ledger_entries` buckets and snapshots |
| `_release_v2_order_collateral`, `cancel_v2_order_collateral`, `reject_v2_order_collateral` | inverse available/locked transfer for legacy contract_version=1 | same two-role linkage; preserve current API/idempotency and guard contract_version=2 |
| Future V2 execution, cancel, expiry, freeze | trade and remaining collateral changes; no matching/order execution writer exists in this repository | `v2_trade` exactly five roles; BUY_LOCKED, BUY_REFUND, SELL_PROCEEDS, SELL_SHARES, BUY_SHARES match original trade ledger identity, before, delta and after, including explicit zero refund; release maps to order-collateral event; no double count of consume snapshots |
| `app/storage.py:init_db`, `_migrate_collateral_ledger_entries` | V1 schema/init, not a V2 bucket movement writer | retain V1 behavior; do not synthesize post-boundary history; V2 init acceptance must validate finalized history without mutation |
| `app/v2_clob_migration.py:migrate_fixture` | fixture-only V1→V2 rebuild | create verified checkpoint and install guards in the same transaction; no operational migration API is authorized |

Per source, every expected role occurs exactly once and every event references one matching finalized source; unknown source, extra/missing role, duplicate association, changed before/delta/after, incorrect bucket or a source without required history fails. For order collateral, the two movement rows reconcile to existing reserve/release ledger; consume event snapshots cross-check trade roles but are not movements. For split/merge, the existing account/reserve ledger and `reserve_events` quantity anchor the history; both YES and NO share movements are captured and checked against the operation. Reconcile account balances and position balances per their own bucket, not per source table or global sum alone. The V1/V2 conservation and audit verifiers remain separate mandatory checks.

## 7. Migration and version policy

V2 schema version 2 may be revised only while its exact schema is confirmed unmerged and never deployed or used for any persistent DB; repository history alone is not proof about every environment. The current implementation exposes only isolated temporary `IsolatedMigrationFixture`; no operational V2 writer or deployed migration is established by this document. Require an explicit verified environment inventory before reusing version 2. Existing disposable old-V2 fixtures may be recreated from fresh V1; they are not evidence that a persistent V2 DB may be discarded. If any persistent V2 DB exists, its prior version-2 schema must be identified by an unambiguous schema/format fingerprint and handled by a separately reviewed forward migration with a verified writer-exclusion gate and checkpoint; do not treat that data as empty, relabel it, or infer old event ordering. Unrecognized, partial, ambiguous or future formats fail closed. If ambiguity cannot be safely disambiguated without a new schema version, allocate a new version under a separate authorized design; no production migration is authorized here.

Checkpoint genesis preserves all prior IDs, `sqlite_sequence` high-water marks, rows, audit hashes and financial state. History begins only at the atomic boundary and makes no claim about complete ordering before it. A verified backup and separate-path restore rehearsal are required before any real migration, not supplied by this design. No old writer may run against the revised V2 schema. Existing features remain disabled. Backup/restore must preserve the whole history, triggers, generation, checkpoint, sequence, source links and audit; validate the saved snapshot using the matching version-aware schema, audit, accounting and history verifiers. A local unkeyed digest does not substitute for authenticated off-host evidence.

## 8. Fail-closed and verification

Reject missing/duplicate/ambiguous buckets, operation context, manifests or source roles; noncanonical type, invalid engine/key, broken FK or wrong schema; unavailable/malformed checkpoint or mismatched count/digest; unfinalized operations; missing/multiple trade roles including zero refund; out-of-order or broken per-bucket continuity; integer overflow/negative value; final live balance mismatch; source/history mismatch; audit or existing conservation violation. Verification is read-only in one consistent SQLite read snapshot, never writes to repair. It reports stable `integrity_status`, `violation_count`, `violation_codes` without exposing participant identifiers; exact new codes and API compatibility must be fixed in implementation tests before shipping. Existing diagnostic JSON keys, `CollateralLedgerError` codes, API and CLI semantics must remain compatible; history failure must be surfaced through the established fail-closed path, without silently dropping old violation codes. A transaction must verify both pre- and post-operation state as applicable, and failures roll back all history and money updates. Existing writers call `_ensure_verified` inside their transaction: the initial check runs before context creation; for the final check the writer first completes source rows, finalizes the manifest and deletes the context, then calls `_ensure_verified` before COMMIT. The public verifier must reject incomplete committed history and must not mistake an authorized in-flight context for a committed state.

## 10. Acceptance matrix and implementation stages

1. Checkpoint empty and nonempty V1 with zero/nonzero point, YES/NO and reserve buckets; verify digest, exact coverage, audit, IDs and original high-water marks; inject rollback at each stage.
2. Bucket creation, bootstrap, allocation, split/merge, BUY/SELL reserve/release and future trade all create the prescribed role set in the same transaction; zero BUY_REFUND exactly once, replay no extra events.
3. SELL_PROCEEDS before/after +1, analogous BUY/refund/share tampering, removed middle event, balanced omission, duplicate/mislinked source, checkpoint removal or tampering, disabled trigger, missing FK or unfinalized context fail closed without repair.
4. Multiple trades/accounts/markets, later reserve/release and split/merge, same timestamp and cross-bucket operations remain valid; order derives only from committed event sequence.
5. Transaction rollback and actual SQLite FULL/IO failures preserve old data; concurrent writers serialize, no history without a balance and no balance without history; AUTOINCREMENT gaps are accepted.
6. Test old V1 variants, incompatible/unknown V2 fingerprints, history-less/incomplete V2, versioned backup/restore and separate-path recovery, fixed API/CLI/JSON/error contracts and feature flags. External-writer exclusion and production readiness require separate evidence.

Next: `V2_BALANCE_HISTORY_SCHEMA_MIGRATION` defines and implements only schema, checkpoint, fixture migration and guard protocol with all necessary writer-scope dependencies explicitly included. Then implement/convert all writers atomically before enabling any V2 writes, followed by reconciliation, init compatibility, backup/restore, end-to-end acceptance and independent review. A schema-only stage must keep V2 writes disabled/fail-closed and must not claim operational or production readiness.
